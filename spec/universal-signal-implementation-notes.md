# Universal signal implementation notes

## Spec observations

- Section 10 requires `exactOptionalPropertyTypes: true`, while §11 says `restale-kit/tsconfig.json` does not change. The former is necessary to reject explicitly supplied `undefined` for forbidden optional `never` fields, so the implementation enables the compiler option.
- `RevokeEventDetail` is specified with `(string & {})` as an allowed custom reason while the testing section requires `'unsupported-target'` to be rejected. A string-intersection cannot exclude that literal, so TypeScript will accept it. The implementation follows the declared public type; a truly enforceable exclusion needs a different custom-reason representation or a finite reason union.
- The spec says an `InlineDataSignal` “does not have” `exact` and a `RevalidateSignal` “does not have” `inlineData` / `markStale`. In a union, plain omitted fields do not reliably reject cross-arm object literals. The implementation uses optional `never` fields to enforce the stated invariants while retaining the intended runtime shape.
- `pushInlineData` is declared unchanged, but its prior `InlineDataResult` carries a separate `signal` plus `inlineData` and previously wrote library-specific `contextHash`. Universal signals prohibit `contextHash`, and an inline-data result cannot safely preserve a revalidation signal's `exact`. The implementation preserves the resolver API by converting a result to `{ key, inlineData, markStale? }` at delivery time and drops the old `contextHash` behavior.
- TypeScript's `any` is assignable to every structural type, so `CacheKey = JSONValue[]` cannot reject a caller-owned `any[]` as §10 claims. It correctly rejects `string[]` and `unknown[]`; rejecting `any[]` requires an API boundary based on generic conditional types rather than an exported structural alias.
- §§11 and 12 conflict on test retention: §11 lists many target-era audit, adapter, and transport tests as unchanged, while §12 explicitly says their target-inference, multi-target, and RTK cases are deleted. The files are retained and migrated in place to assert universal-signal acceptance and rejection of retired routing fields; only the removed RTK adapter and its tests are deleted.
- The broader `docs/` tree is not included in the spec's implementation area and still contains historical target-based guides. The package README and workspace README now describe the universal API; the remaining guides need a dedicated documentation migration or retirement decision.
